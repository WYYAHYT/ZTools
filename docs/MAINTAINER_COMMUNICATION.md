# 维护者沟通与审批规则

- Status: accepted
- Effective: 2026-08-21
- Maintainer: zhangchonghao
- Applies to: all human contributors and development agents
- Authority record: [Baseline 0.1 review](reviews/BASELINE-0.1.md)

## 目的

维护者不需要掌握 ADR、Gate、Contract Gateway 等工程术语，也不应因为看不懂技术细节而被要求盲目批准。本项目由开发 agent 对日常技术判断负责；只有确实需要维护者决定的事项，才向维护者发起审批。

本文件既约束“什么时候必须询问”，也约束“必须怎样询问”。不符合本文件格式、只要求维护者批准某个专业文档或缩写的请求，不构成有效审批。

所有开发 agent 共用本文件和仓库根目录的 `AGENTS.md`。不得为不同 agent 建立互相冲突的审批规则；目录级 `AGENTS.md` 只能补充该目录的实现约束，不能削弱本文件。

## 决策责任

### Agent 直接决定

以下事项默认属于技术执行范围，由当前开发 agent 调研、比较、决定、记录并验证，不要求维护者批准：

- 代码结构、模块划分、接口、数据结构与内部协议细节。
- 依赖库、工具链和精确版本选择，以及无额外费用的 CI 实现细节。
- 错误处理、并发、取消、超时、性能优化和测试方法。
- 安全控制的具体实现，只要不降低已经接受的安全或隐私承诺。
- 在既定产品范围内进行重构、修复、文档同步和工程阶段转换。
- ADR、设计状态、工程基线和其他内部治理记录的技术性决定。

Agent 必须为这些决定承担分析和验证责任。不得因为决定重要、专业或存在多个可行方案，就把技术责任转交给维护者。

### 必须由维护者决定

出现以下任一情况时，agent 必须暂停受影响的动作并请求维护者决定：

1. **产品方向**：改变用户能做什么、首发范围、平台承诺、兼容承诺、默认体验、数据/隐私承诺，或新增账号、同步、市场等产品能力。
2. **费用**：可能产生一次性或持续费用，包括付费服务、云资源、证书、硬件、远程设备和可能计费的 CI。必须先说明金额或可确认的上限；无法估算时明确说明不确定来源。
3. **外部账号或服务**：需要登录、注册、绑定、上传、发布、向第三方发送信息，或操作 GitHub、应用商店、云平台等外部状态。只读访问公开资料不属于产品审批，但执行环境若要求网络授权，仍按工具提示取得授权。
4. **扩大权限或不可逆影响**：需要新的凭据、密钥、系统权限、仓库权限、用户敏感数据访问，降低安全隔离，或者执行难以恢复的删除、迁移和覆盖。

如果一个技术方案会触发以上任一项，agent 应先寻找不触发该项且仍满足目标的方案。不存在合理替代方案时，再请求维护者决定。

## 有效审批请求的固定格式

发给维护者的请求必须使用普通中文，并依次包含以下内容：

```text
需要你决定：<一句话说明用户或项目层面的决定>

为什么现在需要决定：<说明被阻断的工作，以及它属于产品、费用、外部服务还是权限>

我的推荐：<明确推荐一个方案，并说明最主要理由>

你会感受到的影响：
- 产品/用户：<没有则写“无”>
- 费用：<免费、明确金额、上限或不确定性>
- 外部账号/服务：<会操作什么；没有则写“无”>
- 权限和数据：<需要什么、持续多久、如何撤销；没有则写“无”>

其他可选方案：<只列真实可行的替代方案及关键代价；没有则写“无合理替代方案”>

如果暂不决定：<工作会暂停在哪里；不得制造虚假紧迫感>

你可以直接回复：<给出无需理解术语的明确回复示例，例如“按推荐方案”>
```

涉及费用时必须给出币种、计费方式和预计上限；涉及权限时必须给出权限对象、用途、范围、期限和撤销方式；涉及产品方向时必须描述用户可见的前后差异。

一次请求应只包含一个决定，或最多三个紧密相关且能一起判断的决定。不得把一串 ADR、版本号或阶段清单当作一个审批问题。

## 禁止的沟通方式

后续 agent 不得：

- 只说“请 approve ADR-xxxx”“是否关闭 Gate”“请接受 baseline”，却不解释用户可见影响。
- 让维护者在自己无法理解的文档上用“相信 agent”代替知情决定。
- 把依赖版本、目录结构、Schema 形式等纯技术选择交给维护者。
- 用大量术语、链接或原始日志替代结论；技术证据可以附后，但结论必须先用普通中文说明。
- 把“通知你我做了什么”写成“需要你批准”，或在已经越权执行后补要批准。
- 把沉默视为批准，或自行扩大维护者给出的权限、费用和产品范围。
- 为了避免询问而拆分动作、绕过环境授权或隐瞒潜在费用。

## 进度与结果汇报

普通技术工作不需要审批，但 agent 仍应让维护者容易掌握项目：

- 开始时用一两句话说明本轮要得到什么结果，不要求维护者理解内部阶段名。
- 工作中只有出现新风险、范围变化或真实阻断时才打断维护者。
- 完成时先说明已经得到的产品或工程结果，再说明验证情况和仍缺少的真实平台证据。
- 若必须提到 ADR、Gate 或其他术语，第一次出现时立即翻译，例如“ADR（为什么选择这个方案的决策记录）”。
- 维护者询问“我需要做什么”时，第一句必须直接回答“现在不需要你做任何事”或列出唯一需要执行的具体动作。

## 决策与授权留痕

- Agent 自主作出的重要技术决定必须记录候选方案、选择理由、风险和验证方式；可以使用 ADR，但不得要求维护者理解 ADR 才能继续。
- 技术决定的记录写明 `Decider: development agent under delegated technical authority`，并链接本文件和对应提交或评审记录。
- 维护者审批只在收到符合本文件格式的信息并明确回复后成立。记录应引用维护者的原意，并用普通中文概括批准范围。
- 批准范围只覆盖请求中写明的产品变化、金额/上限、外部操作和权限；超出范围必须重新询问。
- 安全策略、工具沙箱和平台自身要求的运行时授权继续有效；本文件不能替代系统授权。

## 示例

### 不需要询问

> 我比较了两个 Schema 校验库，选择维护状态更稳定且更容易生成 TypeScript 类型的方案。这个选择不改变产品功能、不产生费用，也不需要额外权限。我会把理由和验证结果记录在工程文档中。

### 需要询问

```text
需要你决定：首个公开测试版是否购买 macOS 应用签名所需的 Apple Developer 会员。

为什么现在需要决定：不签名仍可继续开发和内部测试，但无法按普通用户期望分发经过公证的 macOS 安装包；这属于外部账号和费用。

我的推荐：临近公开测试版时购买，现在先不购买，避免提前产生年费。

你会感受到的影响：
- 产品/用户：购买后，macOS 用户安装时的安全警告更少，并可走正式公证流程。
- 费用：预计为 Apple 当时公布的年度会员费，购买前再次确认准确金额和币种。
- 外部账号/服务：需要使用你的 Apple Developer 账号完成注册和协议确认。
- 权限和数据：需要发布流程使用签名凭据；凭据保存在受保护环境，不交给开发插件。

其他可选方案：暂不购买，只提供内部未签名构建，但不能把它宣传为正式 macOS 支持。

如果暂不决定：Windows 和 Ubuntu 开发不受影响；macOS 正式分发会在发布前暂停。

你可以直接回复：临近公开测试版时再问我。
```
