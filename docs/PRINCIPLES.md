# 长期原则

- Status: accepted
- Baseline: 0.1
- Last updated: 2026-08-21

本文件记录预期长期稳定的原则。它们高于局部实现便利；改变原则属于 Level 3 变更，必须经过维护者明确批准、新 ADR、威胁分析、迁移与回滚分析。

## 1. 用户控制优先

权限申请必须可理解、与具体动作相关、范围最小，并在系统允许时可撤销。不得绕过 Wayland、操作系统或桌面环境的授权模型来换取表面上的功能完整。

## 2. 默认安全，失败关闭

未知调用者、未知能力、无效输入、权限不明和身份无法确认时默认拒绝。安全边界不得依赖调用方自律，也不得通过关闭浏览器安全选项换取兼容性。

## 3. 核心独立

领域模型和应用规则不得依赖 Electron、Vue、具体数据库、具体操作系统 API 或插件呈现方式。框架与平台只能在外层通过明确接口接入。

## 4. 能力显式化

平台功能以 Capability 表达稳定产品语义；平台实现、外部组件、操作系统授权、运行健康和调用者 Permission 分别表达，不折叠成一个布尔值或单一枚举。Permission 授予某个主体调用 Capability 的资格，但不改变平台本身是否支持或健康。所有维度都必须可查询，而不是隐藏在条件分支和异常里。

## 5. 契约跨越边界

进程、线程、插件和平台组件之间只通过版本化、可验证、可取消和可审计的契约通信。裸 IPC、共享可变全局对象和隐式权限不属于合法架构。

## 6. 平台平等不等于实现相同

Windows、macOS 和 Ubuntu GNOME Wayland 共享产品语义，但可以使用不同 Adapter。无法安全提供的功能应明确降级；不得为了 API 对称伪造能力。

## 7. 插件不等于信任

第三方插件默认不可信。内置体验若需要宿主权限，应作为 Host UI 或明确的受信组件实现，而不是创造可被第三方模仿的“特权插件”通道。

## 8. 生命周期和所有权明确

窗口、Worker、Portal 会话、订阅、快捷键、文件和数据都必须有明确所有者、释放条件和失败恢复路径。插件 UI 与后台 Worker 的生命周期必须分离。

## 9. 可观察但不过度收集

系统应能诊断失败、性能与权限问题，但默认最小化日志和遥测，不记录密钥、剪贴板正文、查询正文或插件私有数据等敏感内容。

## 10. 设计由自动化执行

重要边界最终应由类型系统、Schema、lint、依赖规则、契约测试和 CI 检查执行。文档说明意图，自动化防止无意回退。

## 11. 复用知识，不复用耦合

旧 ZTools 可以提供行为需求、失败经验、数据样本和测试场景，但不能天然证明旧架构适合 vNext。迁移代码必须逐项满足新边界。

## 12. 小步纵向交付

优先用端到端纵向切片验证核心假设。每个切片同时处理正确路径、失败路径、权限、资源清理、平台差异和测试，避免先堆积无法验证的横向框架。
