# 测试策略

- Status: accepted
- Baseline: 0.1
- Last updated: 2026-08-21

## 目的

ZTools vNext 以 Ubuntu 26.04 GNOME Wayland 作为主要开发环境，同时把 Windows、macOS 和 Ubuntu 纳入持续集成与发布门禁。本策略的目标是把大部分正确性放在平台无关、快速且可重复的测试中，只把真正依赖桌面会话、系统授权和硬件行为的验证留给对应真实平台。

Gate 1 的具体操作系统镜像、CPU 架构、runner 与 Electron 版本在 [ENGINEERING_BASELINE.md](ENGINEERING_BASELINE.md) 中固定；本文件定义测试证据等级，不替代该工程矩阵。

测试通过证明的是其覆盖范围内的证据，不自动证明整个产品、某个平台或某项 Capability 已受支持。任何文档或 ADR 只有在对应实现和门禁通过后才能标记为 `implemented`。

## 基本原则

- 测试与生产代码遵守同一依赖方向，不为测试增加生产旁路。
- 每个纵向切片同时测试成功、拒绝、取消、超时、崩溃、资源清理和平台降级。
- 领域规则、契约和大多数 UI 行为应可在任一开发平台重复验证。
- Platform Adapter 使用共享契约测试；真实平台测试只证明 Adapter 和系统集成，不重复组合全部业务场景。
- 托管 CI、虚拟机和 Fake Adapter 各自提供不同证据，不能互相冒充。
- 不稳定测试视为缺陷；不得以无限重试、扩大超时或长期跳过来制造绿灯。
- 测试数据、插件、系统目录和凭据必须隔离，不读写开发者或 CI 用户的真实 ZTools 数据。

## 测试层级

| 层级 | 主要范围 | 默认运行位置 | 是否阻断 PR |
| --- | --- | --- | --- |
| 静态检查 | 类型、格式、依赖方向、禁用导入、安全配置、契约注册完整性 | 三平台 CI | 是 |
| Domain 单元测试 | 纯领域规则、排序输入、状态转换和值对象 | 本机与三平台 CI | 是 |
| Application 测试 | 用例编排、权限策略、取消、事务和失败映射 | 本机与三平台 CI，使用 Fake Ports | 是 |
| Contract 测试 | RPC Schema、Caller Role、错误、版本、超时和取消 | 本机与三平台 CI | 是 |
| Adapter 共享契约测试 | 所有实现必须满足的 Capability 语义 | Fake + 对应平台 CI | 是 |
| 组件测试 | Host UI、可访问性语义和确定性交互 | 无桌面浏览器或 Electron 测试环境 | 是 |
| Electron E2E | 主进程、Renderer、Bridge、窗口与插件隔离链路 | 对应平台 CI/测试机 | 核心用例是 |
| 平台集成测试 | 快捷键、焦点、Portal、密钥库、通知、安装和升级 | 对应真实系统 | 按能力和发布阶段阻断 |
| 安全与故障测试 | 恶意插件、越权、崩溃注入、配额、恢复和损坏处理 | CI + 隔离测试机 | 是 |
| 人工体验测试 | 多显示器、DPI、系统弹窗、桌面交互和可感知性能 | 真实设备 | Preview/Release 是 |

代码覆盖率只用于发现未测试区域，不作为单一质量目标。关键状态、权限和失败边界必须由场景清单证明，不能用总覆盖率替代。

## 开发与 CI 环境

### Ubuntu 主开发环境

- Ubuntu 26.04 LTS、默认 GNOME、原生 Wayland 是日常开发和最完整 Linux 验证环境。
- 开发者本机可以运行 Domain、Application、Contract、组件、Electron E2E 与真实 Wayland 集成测试。
- Portal、D-Bus、PipeWire、Secret Service 与 GNOME Shell 扩展测试必须确认运行在真实用户会话，而不是仅在无桌面的容器中通过。
- 自动测试使用独立临时数据目录、插件目录、旧数据目录、缓存和日志目录；不得读取 `~/.ztools` 或未来正式数据目录。

### 三平台托管 CI

工程骨架建立时创建 Linux、Windows、macOS 矩阵。GitHub Actions 是首选托管方案，但工作流不应把测试语义绑定到单一 CI 提供商。

每个平台至少执行：

- 锁文件与依赖安装验证。
- TypeScript、lint、格式和架构边界检查。
- Domain、Application、Contract 和共享 Adapter 测试。
- Host UI 组件测试。
- Electron 编译、基础启动和可稳定执行的 E2E。
- 对应平台安装包构建检查；未签名 PR 产物不能视为可发布产物。

托管 runner 通常不能可靠验证前台焦点、真实系统授权、多显示器、休眠唤醒、系统密钥环交互、签名信任链和完整升级体验。这些结果必须标注为“构建/自动化证据”，不能升级为“真实平台已验证”。

### 真实 Windows 与 macOS

项目早期可以依赖三平台 CI，不要求立即购买设备。进入平台能力开发后，至少准备：

- Windows 11 x64 的交互式测试环境；Preview 前应有一台真实 Windows 设备。
- Apple Silicon macOS 的交互式测试环境；Preview 前应有真实 Apple 硬件或合规的远程 Mac。
- 当前 Ubuntu 26.04 GNOME Wayland 实机。

Windows VM 可用于安装、卸载、通知、托盘和基础 UI，但不能独立证明多显示器、真实 DPI、GPU、休眠或所有前台窗口行为。Wine 不属于 Windows 支持证据。

macOS 托管 runner 可证明编译和部分自动化；Accessibility、Screen Recording、Keychain、Gatekeeper、签名、公证、Dock/菜单栏和焦点体验必须在真实 macOS 用户会话验证。非 Apple 硬件上的非官方 macOS 环境不进入正式测试矩阵。

## CI 与设备执行节奏

| 触发 | 执行范围 |
| --- | --- |
| 本地提交前 | 受影响的静态检查、单元、契约、组件和窄 E2E |
| 每个 Pull Request | 三平台静态/单元/契约/组件、可稳定 E2E、三平台构建 |
| 合并到主开发分支 | PR 范围 + 扩展 E2E、安全与故障测试 |
| Nightly | 较长的资源、崩溃恢复、安装包 smoke test 和可用测试机平台集成 |
| Milestone Candidate | 三个真实目标平台的能力清单与人工 smoke test |
| Release Candidate | 完整发布门禁、签名/公证、安装/升级/卸载、权限和回滚 |

昂贵的真实设备测试可以按 Nightly、里程碑和候选版本执行，但一等平台的阻断性失败必须在发布前清零或通过正式设计变更调整支持范围。

## Platform Adapter 契约测试

每个 Capability 都提供一套平台无关的共享测试，至少覆盖：

- ADR-0011 已接受的实现支持、外部依赖、系统授权、运行健康和调用者 Permission 五轴状态及其有效组合。
- 成功结果和稳定错误映射。
- 用户拒绝与取消。
- 超时、调用方取消和宿主退出。
- 重复调用、并发限制和必要的幂等语义。
- 权限或依赖在运行期间撤销。
- Handle、订阅、Portal 会话和系统资源清理。
- 日志与审计字段脱敏。

Fake Adapter 用于穷举业务组合；Windows、macOS、GNOME Wayland Adapter 必须在各自系统上运行同一套契约，并增加平台特有的集成测试。Fake 通过不能证明真实 Adapter 已实现。

## Electron 与插件 E2E

Electron E2E 使用打包方式尽量接近生产的应用实例，并为每个测试创建隔离环境。夹具至少包括：

- 正常 Host UI 和宿主命令。
- 最小合法插件。
- Schema 无效、权限不足、超时、崩溃和资源滥用插件。
- 尝试访问 Node.js、Electron、裸 IPC、其他插件数据和宿主私有对象的恶意插件。
- 升级中断、包损坏和卸载清理场景。

测试必须通过公共用户界面或正式 Contract 操作产品，不得依赖测试专用的特权 IPC。允许在测试构建中加入只读、受身份限制的同步点和诊断事件，但它们不能扩大产品权限。

截图和 trace 输出到测试产物目录，不提交版本库。截图前等待页面正文中的稳定特征，而不是仅等待窗口、侧栏或标题出现。涉及插件界面时直接截取插件内容区域，避免用宿主拼接图掩盖生命周期问题。

## 平台发布门禁

### Windows

- 全局快捷键注册、冲突和注销。
- 前台窗口限制、显示/隐藏和先前应用焦点。
- 单/多显示器、不同 DPI 与缩放组合。
- 托盘、通知、登录启动和资源管理器重启。
- 普通用户、管理员/UAC 边界和不同安装位置。
- Credential Manager 的允许、失败与删除。
- 安装、升级、卸载、自动更新、Defender 与 SmartScreen 表现。
- 锁屏、休眠唤醒和系统会话退出。

### macOS

- Intel 支持范围若未来承诺则单独进入矩阵；初始真实设备基线为 Apple Silicon。
- 应用激活、Dock/菜单栏策略、Spaces、全屏应用和焦点恢复。
- 全局快捷键及 Accessibility、Screen Recording 等系统权限的允许、拒绝、撤销和升级保留。
- Keychain 锁定、授权、失败与删除。
- 多显示器、缩放、休眠唤醒和用户会话切换。
- 签名、公证、Gatekeeper、安装、升级、卸载和更新回滚。

### Ubuntu 26.04 GNOME Wayland

- 原生 Wayland 会话中的主窗口召回、隐藏、焦点结果和多显示器缩放。
- Portal 父窗口、允许、拒绝、取消、超时和服务缺失。
- D-Bus 服务重启、PipeWire 会话中断和 Secret Service 锁定/缺失。
- GNOME Shell 扩展未安装、禁用、兼容、版本不兼容、崩溃和 Shell 重启。
- `.deb` 安装、升级、卸载和桌面条目；AppImage 作为辅助格式单独验证。
- 登录启动、通知、锁屏、休眠唤醒和用户会话退出。

## 权限、数据与安全测试

- 每个敏感 Capability 测试未声明、未授权、已授权、拒绝、撤销和插件升级扩大范围。
- 身份必须由连接上下文建立；伪造插件 ID 或 Caller Role 的消息必须失败。
- 存储测试覆盖多插件越权、命名空间、配额、事务回滚、附件部分失败、损坏恢复和卸载策略。
- 系统密钥库测试不得使用开发者真实凭据；使用专用服务名、测试账户或隔离密钥环，并在测试后清理。
- 日志、截图、trace 和失败输出不得包含密钥、令牌、剪贴板正文、查询正文、文件正文或插件私有载荷。
- 测试中创建的 Portal 会话、进程、快捷键、窗口、订阅和临时文件在成功、失败和取消路径都必须释放。

## 测试隔离与可重复性

- 每个测试获得唯一临时根目录，显式传入数据、旧数据、插件、缓存和日志路径。
- 禁止依赖用例顺序、共享用户配置、已有系统授权或外部市场在线状态。
- 时间、随机数、ID 和网络在可行时通过 Port 控制；跨进程测试记录关联 ID 便于诊断。
- 网络测试优先使用本地受控服务；真正的外部服务测试单独标记且不作为普通 PR 的唯一证据。
- 测试结束检查残留进程、窗口、文件锁、快捷键、Portal 会话和未处理 Promise。

## 不稳定测试处理

发现不稳定测试时：

1. 保存日志、trace、截图、平台信息和随机种子。
2. 判断是产品竞态、测试同步错误、环境缺陷还是平台限制。
3. 优先修复所有权、同步点或隔离问题。
4. 若必须临时隔离测试，应建立有负责人、原因、影响和截止条件的跟踪项，并保留替代门禁。

普通重试最多用于收集证据，不能把第二次通过算作稳定通过。不得用固定长时间休眠代替可观察的状态同步。

## 失败产物与隐私

CI 保存与失败相关的结构化日志、测试报告、截图、视频、trace、崩溃转储和安装日志，并设置有限保留期。上传前执行脱敏；包含用户数据或系统机密的产物不得上传。

真实设备和发布签名使用的凭据只存在于受保护环境。来自外部分支或不可信插件样本的工作流不能访问签名、公证、市场或发布密钥。

## 支持声明与退出条件

一项 Capability 在某平台被标记为 `implemented` 或进入 Supported 发布清单前，必须同时满足：

- 共享契约和失败路径测试通过。
- 对应真实 Adapter 集成测试通过。
- 真实用户会话完成关键交互验证。
- 权限、资源清理、安全与隐私检查通过。
- 安装包中的实现经过 smoke test，而不只是源码开发模式通过。
- 已知限制和降级路径已写入平台支持文档。

若当前没有对应真实设备，允许继续开发和合并平台无关能力，但相关平台功能只能标记为未验证或 Preview，不能宣称达到正式支持。
