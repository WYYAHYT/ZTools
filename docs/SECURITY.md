# 安全模型

- Status: accepted
- Baseline: 0.1
- Last updated: 2026-08-21

## 安全目标

- 插件只能代表其自身身份调用已声明且已授权的能力。
- 一个插件的崩溃、恶意输入或资源滥用不能破坏宿主或其他插件。
- 跨进程数据在使用前经过身份确认和 Schema 验证。
- 用户能够理解敏感动作的原因、范围和后果。
- 平台集成遵守操作系统与桌面环境的权限模型。

系统不承诺抵御已经完全控制用户操作系统或宿主安装目录的攻击者。

本文件定义安全架构与强制不变量；受保护资产、攻击者能力、数据流、攻击路径、控制和验证证据在 [THREAT_MODEL.md](THREAT_MODEL.md) 中维护。相关功能的威胁模型未达到对应 Gate 要求时，不得仅凭本文件进入实现。

## 信任区域

| 区域 | 信任级别 | 说明 |
| --- | --- | --- |
| Domain / Application Core | 高 | 保存领域规则，不直接处理不可信平台对象。 |
| Electron Main 与 Host Services | 高 | 管理窗口、进程、身份、权限和 Adapter。 |
| Host UI | 高 | 搜索、设置、市场、账号和权限中心。仍需最小 API 面。 |
| Platform Adapter / Helper | 有限信任 | 能访问特定系统 API；职责、输入和输出必须窄化。 |
| Plugin UI | 不可信 | 沙箱渲染内容，只能通过受控 Bridge 调用。 |
| Plugin Worker | 不可信 | 隔离运行、按插件身份授权，并受资源配额限制。 |
| 外部内容与网络 | 不可信 | 包括网页、下载包、剪贴板和文件内容。 |

## 强制不变量

- 插件渲染环境启用 `contextIsolation`、`sandbox` 和 `webSecurity`。
- 插件不能提供 Electron preload，不能访问 Node.js、Electron或裸 IPC。
- Bridge 只暴露版本化的最小 API，不传递 Electron 对象、文件句柄内部实现或任意回调执行能力。
- 每个请求携带由宿主建立的调用者身份；插件提供的身份字段不能作为信任依据。
- RPC Router 先验证调用者角色、方法、Schema 和权限，再分派请求。
- 未知、缺失、过期或无法验证的信息默认拒绝。
- 敏感能力按最小范围授权，并区分“能力可用”和“用户已授权”。
- 外部 URL、协议、文件路径和插件包在进入受信区域前规范化并验证。
- 机密存入系统密钥库，不得写入普通日志、配置文件或插件可读数据库。

## 类型化 RPC 安全要求

每个方法契约至少声明：

- 方法名和版本。
- 允许的 Caller Role。
- 输入和输出 Schema。
- 所需 Capability 与 Permission。
- 超时、取消和重复请求语义。
- 可返回的稳定错误。
- 是否记录审计事件以及字段脱敏策略。

RPC 返回值不能暴露宿主内部对象。订阅和流必须有背压、取消、断线清理和最大缓冲限制。

## 插件权限

- 插件清单声明可能使用的能力，但声明本身不构成授权。
- 安装时展示权限概览；敏感能力尽量在具体动作发生时请求。
- 授权绑定插件身份、能力和必要范围；插件升级扩大权限时必须重新确认。
- 禁用、卸载或身份变化时撤销活动令牌、订阅和会话。
- 拒绝授权是正常流程，插件必须能得到稳定错误并提供降级体验。

精确的权限文案、授权持久化和一次性授权规则将在首个敏感纵向切片前写入 `PERMISSION_UX.md`。

## 插件执行与资源控制

- Plugin UI 和 Plugin Worker 使用不同执行环境与生命周期。
- Worker 由宿主启动和终止，不允许无限制派生进程。
- 对 CPU 时间、内存、请求并发、消息大小、存储、日志和后台存活设置配额。
- 超时和崩溃采用有限重启与退避策略；连续失败后隔离插件并向用户说明。
- 插件卸载前先停止新请求、取消任务、关闭会话，再处理数据保留或删除策略。

具体配额需要通过性能测试确定，不能在缺少数据时写成稳定插件契约。

## Web 与网络

- Host UI 默认执行严格 CSP，不执行远程脚本。
- 插件网络访问必须经过显式能力和目标范围控制；是否提供直连或宿主代理由后续 ADR 决定。
- 外部网页不得与 Host UI 共享信任上下文。
- 导航、新窗口、下载和自定义协议默认拒绝，由宿主白名单策略处理。

## 供应链

- 依赖使用锁文件和可复现的 CI 安装流程。
- 插件包必须具备完整性校验、稳定身份和来源信息；签名及市场信任策略在分发设计阶段确定。
- 自动更新必须验证来源和完整性，失败时保留可恢复版本。
- 发布产物和原生辅助组件需要平台适用的签名与打包流程。

## Wayland 与系统授权

- Portal 选择器、屏幕共享、远程桌面等系统 UI 是安全边界的一部分，不得自动代替用户确认。
- Portal 会话令牌只授予请求它的主体，并在取消、超时、插件停止或宿主退出时释放。
- GNOME Shell 扩展若被采用，只暴露版本化、最小化接口；安装和启用必须由用户明确完成。
- 不使用依赖合成输入、抓取其他应用内容或绕过合成器策略的隐藏方案。

## 日志与审计

- 安全事件记录主体、能力、结果、时间和必要的关联 ID。
- 默认不记录搜索正文、剪贴板正文、密钥、文件正文、访问令牌或插件私有载荷。
- 调试日志必须有明确启用方式、保存期限和导出前脱敏。
- 审计用于解释授权和失败，不作为无限期用户行为追踪机制。

## 安全变更门槛

任何放宽插件隔离、调用身份、权限检查、浏览器安全选项或系统授权流程的提案都属于 Level 3，按 `DESIGN_PROCESS.md` 执行。
