# 插件模型

- Status: accepted
- Baseline: 0.1
- Last updated: 2026-08-21

## 目标

插件模型应让扩展作者能够贡献丰富的搜索、动作、UI 和后台能力，同时保证插件身份明确、能力最小、故障隔离、协议可演进。

本文件定义新 Secure Runtime 的目标。根据 [ADR-0006](adr/0006-legacy-plugin-compatibility.md)，首阶段不运行旧插件；未来兼容方案必须另行决策，且不得降低本模型的安全边界。

## 插件组成

一个插件包概念上包含：

- Manifest：稳定 ID、版本、协议版本、入口和元数据。
- Contributions：命令、搜索 Provider、动作、视图和设置声明。
- Capability Declarations：可能请求的宿主能力及必要范围。
- Plugin UI：可选的沙箱界面资源。
- Plugin Worker：可选的后台入口。
- Assets：图标、静态资源和本地化内容。
- Integrity Metadata：来源和完整性信息；精确签名策略后续确定。

Manifest 的正式 Schema 必须通过 ADR 和契约版本发布，不能仅以 TypeScript 接口充当运行时验证。

## 身份

- 插件身份由宿主安装记录和包完整性共同建立，不能由运行时代码自报。
- UI、Worker、存储、权限和日志都绑定同一插件身份，但拥有不同 Caller Role。
- 插件升级不能借版本变化获得新权限；能力范围扩大时重新请求授权。
- ID 冲突、来源变化或完整性失败时默认停止加载。

## UI 与 Worker 分离

### Plugin UI

- 负责展示和短时交互。
- 在沙箱 Renderer 中运行，无 Node.js、Electron、裸 IPC 和自定义 preload。
- 只能通过版本化 Bridge 请求宿主 API。
- 关闭视图后，UI 订阅和会话必须释放。

### Plugin Worker

- 负责搜索 Provider、后台计算和有限的事件处理。
- 生命周期由宿主管理，可因空闲、升级、超时、配额或故障被终止。
- 不能依赖 UI 存活，也不能把内存状态当作持久保证。
- 后台唤醒来源、频率和最长存活必须受策略控制。

UI 与 Worker 通过宿主中介或插件私有存储协作，不共享可变 JavaScript 全局对象。

## 贡献模型

首批候选贡献点包括：

- Command：可直接发现和执行的命令。
- Search Provider：根据查询异步、增量返回结果。
- Action：作用于结果或用户输入的结构化动作。
- View：在插件沙箱中展示的交互界面。
- Settings Schema：由 Host UI 渲染或安全传递的插件设置描述。

新增贡献点属于公开插件协议变化，至少按 Level 2 处理。

## API 设计规则

- 默认异步；只有纯本地、无失败分支且性能有严格保证的读取才可考虑同步。
- 每个 API 对应明确 Capability、Caller Role、Schema、错误、超时和取消语义。
- 不暴露通用 `invoke(channel, payload)`、任意文件路径访问或宿主对象句柄。
- 对文件、目录、窗口、屏幕流等资源优先返回受范围限制的逻辑 Handle；Handle 不可伪造、可撤销且有生命周期。
- API 采用显式版本与兼容窗口；弃用先告警、再按支持策略移除。
- 批量与流式 API 必须定义分页、背压和最大消息大小。

## 权限关系

```text
插件声明 Capability
        ↓
平台分别报告实现、外部依赖、系统授权和运行健康
        ↓
用户或策略决定插件 Permission
        ↓
每次调用仍验证身份、范围、状态和输入
```

安装清单、平台实现、外部依赖、系统授权、运行健康和调用者 Permission 缺一不可。安装成功、系统已授权或插件曾获持久 Permission，都不能单独证明当前调用可执行。

## 生命周期

插件至少具有以下概念状态：未安装、已安装、已启用、运行中、已暂停、已禁用、升级中、隔离、卸载中。具体转换、并发事件和恢复策略将在实现前写入 `state-machines/plugin-lifecycle.md`。

生命周期要求：

- 启用前验证 Manifest、协议、完整性和平台要求。
- 升级时停止接收新任务，处理旧任务并以原子方式切换版本。
- 崩溃采用有限重启；持续失败进入隔离而非无限循环。
- 禁用和卸载立即撤销活动调用、订阅、Handle 与 Worker。
- 数据删除和保留必须遵循后续 `DATA_OWNERSHIP.md`，不能由目录删除副作用决定。

## 存储

- 每个插件只能访问自己的逻辑命名空间。
- 插件不能打开宿主数据库、其他插件数据或真实密钥值。
- 大对象与结构化数据可以采用不同后端，但对插件暴露统一、受配额 API。
- 敏感值使用系统密钥库并仅通过不泄漏内容的引用管理。

最终后端选择见 [ADR-0008](adr/0008-storage-strategy.md)。

## 开发与调试

- 开发模式不能降低生产安全边界，只能增加明确标识的诊断能力。
- 插件日志带插件身份并脱敏，用户能单独导出或清理。
- 提供契约测试工具，允许插件作者在不启动完整桌面的情况下验证 Manifest、Schema 和权限降级。
- 本地未签名插件的安装必须有清楚提示，并与市场来源区分。

## 兼容原则

- 新协议从第一次发布起版本化。
- 宿主先协商协议，再创建运行环境；不兼容时给出可操作错误。
- Secure Runtime 不为兼容旧插件而放宽隔离。
- 若未来建立 Legacy Runtime，它必须使用独立进程、明确风险提示和独立权限策略，不能成为新插件的可选逃生口。
