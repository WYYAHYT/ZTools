# 设计变更流程

- Status: accepted
- Baseline: 0.1
- Last updated: 2026-08-21

## 目的

本流程用于保持原则、当前设计、ADR、实现与测试一致。它既防止把临时实现升级为架构，也防止文档成为无法调整的负担。

## 文档角色

| 载体 | 作用 | 修改方式 |
| --- | --- | --- |
| `docs/PRINCIPLES.md` | 长期产品与工程原则 | 仅 Level 3 变更 |
| 主题设计文档 | 描述当前目标设计与开放问题 | 随已批准设计同步更新 |
| ADR | 记录一项决策当时的背景、选择和后果 | 接受后不改写结论；用新 ADR 取代 |
| `AGENTS.md` | 规定开发流程、硬性约束和文档路由 | 随治理流程更新，不承载详细设计 |
| 代码与测试 | 已实现行为和可执行约束 | 不得反向静默覆盖设计 |

## 状态词

- `draft`：仍在形成，不能当作稳定承诺。
- `proposed`：存在明确提案，等待批准。
- `accepted`：已经批准，允许据此实现。
- `implemented`：已批准且对应范围已经验证落地。
- `deprecated`：不再推荐或已计划退出。
- `superseded`：已被另一份 ADR 或设计替代。

设计被接受与代码已实现是两件事。主题文档通常用 `draft` 或 `accepted`；ADR 可以沿上述完整生命周期变化。

## 变更等级

### Level 0：勘误

适用于错别字、坏链接、排版和不改变语义的澄清。可以直接修改，但不得借“勘误”改变范围、边界或承诺。

### Level 1：设计补充

适用于不改变既有模块责任、信任边界、公开契约和平台承诺的补充。应同步主题文档、实现与测试，并在变更说明中指出补充内容。

### Level 2：架构变更

满足任一条件即属于 Level 2：

- 改变模块所有权、进程边界或依赖方向。
- 新增或改变公开插件协议、RPC 或持久化格式。
- 改变 Capability、权限或平台降级语义。
- 引入新的系统组件、运行时或关键基础设施。
- 取代一个已接受 ADR。

必须先创建状态为 `proposed` 的 ADR，列出替代方案、安全与迁移影响，取得维护者明确批准后，才可以实现。

### Level 3：原则、安全或产品承诺变更

满足任一条件即属于 Level 3：

- 放宽默认安全、插件隔离或用户授权原则。
- 改变核心产品边界或一等平台承诺。
- 引入不可逆数据迁移、隐私风险或重大兼容承诺。
- 修改 `docs/PRINCIPLES.md` 的语义。

除 Level 2 要求外，还必须提供威胁分析、用户影响、迁移方案、回滚方案和明确的维护者批准记录。

## 标准流程

1. 描述用户问题和约束，不先绑定实现方案。
2. 定位受影响的原则、主题文档、ADR、契约和测试。
3. 判断变更等级；拿不准时按更高一级处理。
4. 对 Level 2/3 创建 proposed ADR，至少比较两个真实可行方案。
5. 在批准前允许做隔离、可丢弃的技术验证，但必须先记录验证目标、候选范围、位置、负责人、外部资源权限和清理方式；验证代码、锁文件和生成物不得直接合并成产品架构或发布承诺，只能把证据和设计结论带回正式分支。
6. 获得批准后更新 ADR 状态和当前设计文档，再实施纵向切片。
7. 用类型、Schema、lint、边界测试和 CI 固化关键约束。
8. 验证完成后，把相应文档或 ADR 从 `accepted` 更新为 `implemented`；只能更新状态与实施记录，不能改写原始决策。

## ADR 不可改写规则

已接受 ADR 的背景、决策和后果原则上不可重写。若决策变化：

1. 创建新的 ADR，并在其中填写 `Supersedes`。
2. 将旧 ADR 状态改为 `superseded`，填写 `Superseded by`。
3. 更新主题设计文档，使其只描述新的当前设计。
4. 保留旧 ADR，确保历史原因可追溯。

允许对旧 ADR 做不改变语义的勘误、补链接和追加实施记录。

## 批准与基线证据

- ADR 从 `proposed` 转为 `accepted` 时，填写 Accepted 日期、具体 Decider 和可追溯 Approval record。
- Approval record 可以是 Issue、PR、评审会议记录、仓库内评审记录或包含决定的基线提交；不得只写“已讨论”。
- 基线首个提交创建前，允许临时链接 `docs/reviews/` 并标记 `commit pending`；提交后应补充哈希。
- Reviewers 记录参与安全、平台、产品或工程评审的具体人员/来源；Verification owner 对实施证据负责，不等于 Decider。
- Gate 关闭必须有独立评审记录和明确授权，不能从若干 accepted ADR、CI 绿灯或提交存在自动推断。
- 已冻结 Baseline 的 accepted ADR 结论不改写；基线冻结前的范围修正也必须在评审记录中说明，避免把候选稿历史伪装成稳定历史。

## 紧急修复

安全或数据损坏问题可以先实施范围最小、可回滚的止血措施，但必须：

- 不扩大权限或关闭隔离。
- 在变更中明确临时性质、风险和回滚条件。
- 尽快补齐相应 ADR、威胁分析和永久方案。

紧急情况不是长期绕过设计流程的理由。

## 评审检查项

- 问题是否真实存在，还是为假设需求预建框架。
- 是否保持领域核心独立和依赖方向。
- 是否改变调用者身份、权限、数据所有权或失败边界。
- 各目标平台是否有真实实现或明确降级。
- 插件、Portal 会话和资源能否被取消、回收与审计。
- 是否存在兼容、迁移、隐私和回滚影响。
- 哪些规则可以被自动化验证。
